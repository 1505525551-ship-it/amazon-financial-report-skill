# 输出说明

一份工作簿三个 sheet，所有金额保留两位小数、按原币种记账，不做汇率换算。

工作簿的范围是"一个文件夹"：输入目录只有一个文件夹时就一份，下面套了月份文件夹时，每个月份各一份，表里只含那个文件夹的数据。

平时是三个 sheet。数据里有没进配置的费用项、或者有没匹配上平台行为的交易时，会多一个"待补清单"页，把该补的东西列清楚，见第八节。

## 一、校验核对

一组（同名 csv + pdf）一行，明细与汇总的核对结论都在这里。  
**注意：csv和pdf必须同名**

| 列 | 含义 |
| --- | --- |
| 文件名 | 去掉扩展名的原始文件名 |
| 期间 | 报表所属月份，`yyyymm`，如 `202606` |
| 币种 | 优先取 summary 识别结果，没有 summary 时取明细识别结果 |
| 明细报告total | csv 的 total 列逐行合计，已按币种小数规则转换 |
| 收入 / 费用 / 转账 / 税 | summary 顶部 Totals 区四行金额 |
| debt | 转账分类里"信用卡扣款及其他债务回收"的贷方金额 |
| 平台应收净额 | 收入 + 费用 + debt，不含转账与税 |
| 差异 | 明细报告total 减（收入 + 费用 + 转账 + 税），带符号 |
| 汇总和明细报告核对 | L 列，表间核对：通过写绿色"核对一致"，否则红字差额绝对值 |
| 汇总报告核对 | M 列，summary 自身核对：区块逐项 = 小计、小计 = 页首四项 |
| 日期范围报告核对 | N 列，明细逐行金额自洽：product_sales..other 之和 = total |

结论判定：

- L 列：`|差异| <= 容差（默认 0.01）` → 绿色"核对一致"；否则红字写差额绝对值
- M / N 列：内部差额合计为 0 → 绿色"核对一致"；否则红字写差额绝对值汇总数
- 只有 csv → L 写"仅明细"，N 照常核对；只有 pdf → L 写"仅summary"，M 照常核对；缺的那一侧留空

平台应收净额里加 debt，是因为信用卡代扣回收直接冲抵平台应付，不等于银行转账：转账是资金账号间划拨，税是代收代付，两者都不进平台应收。

## 二、Summary全字段

一行一个费用项，窄表展示。

| 列 | 含义 |
| --- | --- |
| 文件名 | 去掉扩展名的原始文件名 |
| 店铺显示名 | pdf 右上角 Display name，卖家自取的店铺名 |
| 法定名称 | pdf 右上角 Legal name，营业执照主体名 |
| 报表期间起 / 止 / 币种 | 与校验核对表一致，便于换汇归集 |
| 分类 | 收入 / 费用 / 转账 / 税，对应 pdf 里的四个区块 |
| 字段原文 | pdf 里显示的原样文字，长名称被 pdf 截断时按截断结果保留 |
| 中文标准字段 | 按 `summary_report_field.csv` 翻译，跨站点汇总用这一列 |
| 借方 / 贷方 | 该字段在 Debits、Credits 两列的金额 |
| 净额 | 借方加贷方 |

同一家店的几个站点，法定名称往往是同一个主体，按法定名称汇总等于把主体合并了。要分店铺看，就用店铺显示名那一列。显示名和法定名一样，说明卖家当初没单独设过店铺名。

小计行不写进明细，只拿来做汇总报告核对（M 列）。对照表里查不到的字段，中文列空着，脚本跑完会单独列一份清单出来。

## 三、明细总表

| 行 | 内容 |
| --- | --- |
| 第 1 行 | 标准字段英文名，与配置表 A 列一致 |
| 第 2 行 | 标准字段中文名，与配置表 B 列一致 |
| 第 3 行起 | 数据 |

逐行金额自洽（十八个金额列之和减去 `total`）不再写进明细表，改成每行取绝对值累加，结果放在"校验核对"的 N 列。正常为 0，即绿色"核对一致"；不为 0 时 N 列红字给出差额绝对值汇总数。

金额列是数字格式 `#,##0.00`，可以直接求和、做透视。

## 四、三列核对

抓完数字不能直接信。脚本从三个方向各算一遍，结果分别落在 L、M、N 三列：

| 列 | 名称 | 层级 | 算法 |
| --- | --- | --- | --- |
| L | 汇总和明细报告核对 | 表间 | 明细 total 合计 − summary 四项合计 |
| M | 汇总报告核对 | 表内 | 区块逐项 vs 小计、小计 vs 页首，各差额取绝对值累加 |
| N | 日期范围报告核对 | 表内 | 每行 product_sales..other 之和 − total，取绝对值累加 |

任一层不过，工作簿照常生成，只是对应列变成红字差额；L 不过同时会让该组计入"核对失败"。

## 五、常见失败与处置

| 现象 | 原因 | 处置 |
| --- | --- | --- |
| 差异是整数、金额接近 | csv 与 pdf 不是同一期 | 核对文件名里的月份，重新导出同期文件 |
| 大批量仅明细 | 文件夹里没放 summary 或命名不一致 | 让 csv 与 pdf 去掉扩展名后完全同名 |
| 某币种全部解析失败 | `summary_report_keyword.csv` 缺该币种 | 看 pdf 顶部 Totals 四行原文，补一行 |
| 识别币种失败 | 货币说明句没进配置 | 把 csv 或 pdf 里的说明句原样补进 `common_currency_mapping.csv` |
| 中文标准字段大量为空 | 对照表缺项 | 按 `未匹配到中文的字段` 清单逐条补 |
| 平台行为列有空值 | 该 type 不在行为规则里 | 按 `平台行为没匹配上的交易` 清单补规则，注意放在兜底行之前 |
| M 列写"核对异常" | pdf 缺小计行或页首四项没认全 | 看该份 pdf，多半是语种关键字没进配置 |

## 六、配置改动注意

- `detail_report_behavior.csv` 是"且"匹配：type 与关键词都要满足，任一列为空则该列不限制。从上往下取第一条命中的规则，新增细分规则要放在对应兜底行之前，比如 `平台服务费-其他（Service Fee 类）` 之前
- 配置文件名与首行列名被脚本按位置读取，不要改名或插列
- `summary_report_keyword.csv` 四列顺序固定为 收入 / 费用 / 转账 / 税，顺序错会导致金额串行、核对必然失败
- `summary_report_field.csv` 的原文列按 pdf 实际显示填写，被截断的长名称按截断结果填，脚本支持前缀匹配
- 币种靠 `common_currency_mapping.csv` 的货币说明句识别，csv 与 pdf 共用，忽略大小写；句子没命中时用同表的关键词列兜底；金额格式由 `common_number_mapping.csv` 按币种指定，未列出的按中英美格式解析
- `report_field_mapping.csv` 同一 summary 字段可以写多行，脚本把命中该字段的各行明细相加。用于一个字段在明细里分散到多个行为的情况，各行的行为或 type 条件必须互斥，否则同一笔明细会被重复计入
- 日本站的促销返点税（promotional_rebates_tax）属于向买家收取的销售税，summary 已把它从商品/运费/包装税费中净额扣掉，所以这类税规则要把该列一并纳入，否则日本站会整组多算一个折扣税额

## 七、已知限制

- 报表期间只认英文月份缩写和 `YYYY年M月D日` 两种写法，其他本地化日期会留空
- 明细字段映射目前覆盖 USD、CAD、MXN、JPY、BRL 五个币种列，其他币种要自己在 `detail_report_field.csv` 加列
- `summary_report_keyword.csv` 现在只有 USD、CAD、MXN、BRL、JPY 五种。碰到欧元、英镑等站点，先在 pdf 顶部 Totals 找到四行原文再加一行，否则那份会解析失败
- 明细的列数和顺序跟着配置表走，配置表增删字段会直接改变输出表结构

## 八、字段核对

summary 的每个费用项，回日期范围报告里按规则汇总后比金额。一组一组列，末尾有合计行。

| 列 | 含义 |
| --- | --- |
| 期间 | 报表期间，yyyymm 格式 |
| 文件名 | 去扩展名的原始文件名 |
| 分类 | 收入 / 费用 / 税 / 转账 |
| summary字段 | pdf 里的原文，合并组用 ` / ` 连起来 |
| 中文标准字段 | 对照表翻译后的名称，合并组同样用 ` / ` |
| summary金额 | summary 里该字段的净额（借方 + 贷方） |
| 明细金额 | 按映射规则从明细汇总出来的金额 |
| 差异 | summary 金额减明细金额 |
| 日期范围报告明细的取数规则 | 用了哪些金额列、哪些平台行为、正负筛选 |
| 核对结果 | 核对一致（绿）/ 差额（红）/ 未配置 |

取数规则在 `config/report_field_mapping.csv`：

| 列 | 说明 |
| --- | --- |
| summary字段 | 必须与 `summary_report_field.csv` 的中文标准字段一致 |
| 分类 | 收入 / 费用 / 税 / 转账，同一中文在不同分类下可以各配一条 |
| 币种 | 留空为通用；写 JPY 等则只对该币种生效，币种专属优先 |
| 取数列 | 明细的金额列，多个用 `|` 分隔，按行相加 |
| 行为 | 平台行为，多个用 `|`，支持 `调整-*` 结尾通配；留空表示不限 |
| type条件 | 明细原始 type，多个用 `|`，精确匹配、忽略大小写；留空不限 |
| 描述关键词 | 明细 description 包含任一关键词即算命中，多个用 `|`；留空不限 |
| 条件 | `any` 全部、`pos` 取数列为正、`neg` 为负 |
| 核对组 | 留空各自核对；填相同组名的多行合并成一行，用于明细无法拆分的场景 |
| 说明 | 备注，仅作维护提示 |

取数时四层过滤同时生效：行为、type、描述关键词、符号。summary 是窄表（一行一个字段），明细是宽表（一行多个金额列），这一步就是把宽表按条件压成窄表再比。行为列本身就是 type + 描述匹配出来的结果，写着更易读；type 与描述两列留空即可，需要更原始的口径（比如同一行为跨多个 type）时再填。

合计行为什么重要：summary 会把同一笔钱归到不同字段（典型是税差并入 FBA 退款、佣金返还与退货管理费轧差）。逐字段差额可能不为零，但只要合计为零，说明只是归类口径不同，钱没丢；合计不为零才是真差异。

## 九、待补清单

只在有东西要补的时候出现，数据干净的工作簿里没有这一页。

| 列 | 含义 |
| --- | --- |
| 类型 | 未匹配中文字段 / 未匹配平台行为 |
| 分类 | 前者是收入、费用、转账、税；后者固定写"明细 type" |
| 原文 / type | pdf 里的费用项原文，或 csv 里的 type 值 |
| 出现次数 | 本文件夹里出现了多少行 |
| 示例描述 | 未匹配平台行为时给一条样例描述，方便判断该归到哪个行为 |
| 补到哪里 | 该往哪个 csv 加一行 |

补完重跑一次，这页就会消失。
